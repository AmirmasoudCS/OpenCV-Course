# Session 5 — Geometric Transformations

## Overview

This session covers the operations that move pixels around in space rather than changing their values: translation (shifting), rotation, and flipping. Where Session 4's operations changed *what* each pixel represents (color, sharpness, intensity), these transformations change *where* each pixel ends up. Translation and rotation share a common mathematical backbone — the affine transformation matrix — while flipping is handled as a separate, simpler special case.

## Files

- `main.py` — menu-driven entry point demonstrating translation, rotation, and flipping
- `translation.py` — shifts an image along the X and/or Y axis
- `rotation.py` — rotates an image around a given point (or its center)
- `flip.py` — mirrors an image over the X-axis, Y-axis, or both

## Core Philosophy

**Translation and rotation are both instances of the same underlying idea: an affine transformation matrix applied via `warpAffine`.** Rather than being separate operations conceptually, both `translate()` and `rotate()` construct a 2×3 matrix describing *how* every pixel's coordinates should be remapped, then hand that matrix to `cv.warpAffine()` to actually perform the remapping. Translation's matrix is almost trivial — an identity matrix with an offset column added — while rotation's matrix is generated by `cv.getRotationMatrix2D()`, which encodes the trigonometry of rotating around a point. Recognizing that both are "just" matrix transforms applied the same way is more valuable than memorizing each function individually — it means learning `warpAffine` once, and understanding it, unlocks a whole family of geometric operations, including ones not covered explicitly here (like shearing).

**Translation's matrix is where the direction convention lives, and it's worth internalizing rather than guessing.** The matrix `[[1, 0, x], [0, 1, y]]` shifts every pixel by `x` horizontally and `y` vertically — but because image coordinates grow downward and rightward (not upward, like a typical math graph), positive `y` moves the image *down*, not up. This is a quiet but important inversion from standard Cartesian intuition, and the code's comments exist specifically to flag it because it's an easy thing to get backwards.

**Rotation defaults to the image's own center for a reason: it's the "expected" behavior in almost every practical case.** When `rotation_point` is `None`, the code computes the midpoint of the image and rotates around that. Rotating around any other point is still fully supported — the function accepts an arbitrary `(x, y)` — but defaulting to the center means the common case (spin the image in place) doesn't require the caller to do any math first. This is a good instance of a sensible default that doesn't limit flexibility.

**`warpAffine` needs to know the *output* canvas size, and that's a subtle but important detail.** Both `translate()` and `rotate()` pass `dimensions = (width, height)` — the *original* image's dimensions — as the target size for the warped output. This means pixels that get shifted or rotated outside those original bounds are simply clipped, not expanded into a larger canvas. For rotation in particular, this means rotating a non-square image by 90° can visibly crop the result, since the output frame doesn't grow to fit the new orientation. This isn't a bug in the code — it's a property of `warpAffine` that's worth understanding rather than being surprised by.

**Flipping doesn't need a transformation matrix at all, because it isn't really an affine transform in the same spirit — it's a direct reordering.** `cv.flip()` is a single dedicated function rather than a matrix-and-`warpAffine` combination, because mirroring an image is conceptually simpler: it's just reversing the order of rows and/or columns. The `flip_code` values (`0`, `1`, `-1`) map directly onto "flip vertically," "flip horizontally," and "flip both," and there's no coordinate math to reason about the way there is with rotation. This session deliberately shows two different implementation strategies — general matrix transforms for translation/rotation, and a specialized direct function for flipping — because OpenCV provides both, and recognizing which one a given task calls for is part of using the library efficiently.

## Key Takeaways

| Concept | Why it matters |
|---|---|
| `warpAffine` + a 2×3 matrix | Common backbone for both translation and rotation |
| Translation matrix `[[1,0,x],[0,1,y]]` | Minimal case of an affine transform — a pure offset |
| +y moves down, not up | Image coordinates are inverted from typical math intuition |
| Rotation defaults to image center | Sensible default; explicit point still fully supported |
| Output size = input size | Warped content outside original bounds gets clipped, not expanded |
| `cv.flip()` is not matrix-based | Mirroring is row/column reversal — simpler than a general affine warp |
